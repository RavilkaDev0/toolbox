# ADR-0006: Browser Images to PDF

- **Status:** TBX-004 implementation.
- **Scope:** One converter. No backend processing, uploads, persistence or universal engine framework.
- **Ownership:** `core` contains signature/dimension inspection, limits, proportional page geometry and immutable ordering. `contracts` validates metadata/options with Zod. `browser-engines` decodes, normalizes, generates and verifies PDF bytes, and renders an actual PDF page. The web workspace owns UI and two browser worker entry adapters.
- **Cancellation:** One active conversion/validation worker per workspace. Cancel/reset/unmount terminate it, abort any main-thread canvas fallback, and invalidate its generation. Bitmaps close and canvases shrink in `finally`; thumbnails/PDF URLs revoke on replacement/removal/reset/unmount. The PDF preview has a separate bounded, cancellable page render and destroys its document/worker after each page.
- **Browser compatibility:** Use `createImageBitmap` with EXIF orientation. Prefer OffscreenCanvas in a worker; WebKit without it uses a sequential HTML canvas adapter on the main thread. JPEG is re-encoded at quality 0.95, PNG/WebP to PNG with alpha. Strip input metadata. Static images only; animated PNG/WebP are rejected. Canvas/browser color conversion is not archival color management.
- **Geometry:** One image per page, input order preserved. Auto uses 96 px/in, no margins/orientation override/crop. A4/Letter use explicit portrait/landscape and 0/10/20 mm margins. Fit contains the whole image; Fill covers and clips the content rectangle. White page background preserves alpha appearance without flattening the PNG mask.
- **Limits:** 10 files, 8 MiB each, 32 MiB total, 8192 px per side, 12 MP per image and 24 MP per selection; inspect before decoding and recheck decoded dimensions. Normalized encoded image bytes cap at 48 MiB; PDF output caps at 64 MiB. Sequential decoding and 320 px thumbnails limit simultaneous pixel buffers. These are upper bounds, not a guarantee against every mobile browser's memory pressure; large batches must be split.
- **Result:** Reopen serialized PDF using pdf-lib and verify all page counts/sizes before returning success. PDF.js renders actual generated bytes one page at a time, maximum 640 × 800 canvas, independent of native PDF viewer support. Download/open remain available on a preview failure. No source files, names, PDF bytes or errors are sent to analytics/network.
- **Dependencies:** `pdf-lib@1.17.1` (MIT, 19,461,112 installed bytes) was explicitly requested. Alternatives are jsPDF or an unmaintainable custom writer; older upstream release and PNG intermediate memory need fixture/security review. `pdfjs-dist@6.3.289` (Apache-2.0, 34,781,083 installed bytes) is necessary for consistent actual output preview; native iframe viewers were blank or initiated unintended downloads in tested browser profiles. Its optional Node-only `@napi-rs/canvas` (MIT, platform binary around 15 MiB) is a package install dependency and never used by browser processing. Main/worker rendering bundles are local and loaded only for the tool's result, no CDN. Installed size is not the shipped compressed browser size. Both libraries and all transitives are locked; web's pdf-lib dev dependency inspects downloaded test PDFs.
- **Build/testing:** Contracts now depends on pure core limits/types; workspace package builds run topologically instead of racing under `--parallel`. Playwright uses two workers to bound concurrent large-image fixtures and development compilation on local/CI machines; assertions and timeouts remain intact. Synthetic fixtures include real format binaries, EXIF/alpha/animation/corruption/resource ceilings. Native viewer support is not used as proof of successful rendering.
- **Publication:** Only Images to PDF may become published after gates and binary/browser checks. The other 14 definitions remain draft; links filter publication state. No merge/release/deploy is authorized by this ticket.
