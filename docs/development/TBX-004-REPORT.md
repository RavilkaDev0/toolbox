# TBX-004 — Images to PDF verification report

Implemented from `dev` commit `3a6da2fbe473c2b2b65dce3d4573d2703582e6cf` on `feat/tbx-004-images-to-pdf`. PR #3 was already merged before work started. Verification date: 2026-10-11. No merge, release or deployment was performed.

## Architecture and behavior

`packages/core` owns bounded signature/header inspection, PNG CRC checking, WebP container/bitstream agreement, proportional page geometry and immutable ordering. `packages/contracts` owns strict Zod metadata and settings schemas. `packages/browser-engines` owns browser decoding, normalization, PDF generation, serialized-result verification and actual PDF rendering. `apps/web` owns selection, drag/drop, keyboard ordering, settings, worker adapters, cancellation and result UI. API/worker/server-engine workspaces have no processing changes.

One active validation/conversion worker processes images sequentially. Cancel, reset and navigation terminate the worker, abort a canvas fallback and invalidate older callbacks. ImageBitmaps close and temporary canvases shrink in `finally`. Thumbnail/PDF Blob URLs revoke on replacement, removal, reset and unmount. Buffer references die with the completed/terminated worker; garbage collection is browser controlled. PDF preview renders one generated page at a time and releases its document/worker after each render.

WebKit in the tested profile lacks worker OffscreenCanvas, so its worker requests a sequential browser HTML-canvas adapter. This is a real browser conversion, with no backend fallback. Native PDF iframe rendering was inconsistent across test profiles; local PDF.js renders the generated bytes instead. A preview failure preserves the verified PDF download and explains how to open it.

JPEG is normalized at quality 0.95 with browser-applied EXIF orientation. PNG and static WebP normalize to PNG retaining alpha. A white PDF page makes transparency predictable. A4/Letter support portrait/landscape, 0/10/20 mm margins and proportional Fit/Fill with clipping. Auto uses 96 pixels per inch and disables inapplicable options. One image creates one page, preserving the selected order.

## Limits and memory rationale

| Limit | Value |
| --- | --- |
| Selection | 10 files |
| Compressed input per file / total | 8 MiB / 32 MiB |
| Decoded image / selection | 12 MP / 24 MP |
| Longest side | 8192 px |
| Normalized encoded images / final PDF | 48 MiB / 64 MiB |
| Thumbnail / PDF preview | 320 px longest side / maximum 640 × 800 canvas |

12 MP occupies approximately 48 MB as one RGBA pixel buffer, before bitmap/canvas/codec/PDF copies. Sequential decoding, small thumbnails and flushing each embedded image prevent retaining every decoded image at once. Header dimensions are checked before decoding, and decoded dimensions are checked again. A WebP envelope claiming smaller dimensions than its compressed payload is rejected before decoding.

These bounds favor mobile use over unbounded camera batches. They do not guarantee a memory peak below a device's tab limit: browser codecs and PDF serialization make additional allocations. The tested 390 px viewport is a desktop browser viewport, not physical phone hardware. Users with larger images/batches must resize or split their selection. Animated PNG/WebP and other formats are explicitly rejected.

## Dependencies and lazy loading

| Dependency | Reason / license | Installed size | Production asset size (raw / gzip) |
| --- | --- | --- | --- |
| pdf-lib 1.17.1 | Requested PDF writer; MIT | 19,461,112 B | 429,791 / 177,262 B |
| pdfjs-dist 6.3.289 | Consistent preview of actual generated PDF; Apache-2.0 | 34,781,083 B | Main: 455,728 / 135,395 B; worker: 1,183,190 / 363,684 B |

Versions/transitives are pinned in `pnpm-lock.yaml`. PDF.js has an optional Node-only MIT canvas package, with a platform binary around 15 MiB; it is not used by browser processing. Installed package size is different from browser transfer size. The writer imports on conversion; the viewer imports for a result. The production homepage loaded none of these heavy chunks. All assets are local; there is no CDN dependency.

Alternatives considered: jsPDF or a custom writer for generation, native PDF iframe for display. pdf-lib was explicitly requested; a custom writer would increase correctness risk. Native display failed the actual-preview criterion in tested profiles. pdf-lib's older upstream release and PNG intermediate memory remain maintenance concerns; PDF.js adds a substantial result-preview download. See [ADR-0006](../decisions/ADR-0006-images-to-pdf.md).

## Publication, changed areas and remaining risks

Only `images-to-pdf` is published in the registry. The other 14 tools remain draft; no placeholder route becomes public. Homepage/catalog/category counts and links derive from registry state; the real tool has semantic metadata, privacy/quality copy, instructions and a working PDF-category link. Production private fixture and draft URLs return 404.

Changed areas: core rules/catalog/tests; contracts schemas/tests; browser engine/conversion/preview/tests; web worker/UI/route/catalog copy; shared dropzone label/cancellation copy; meaningful catalog/browser tests; pinned dependency lockfile; ordered package build; architecture, quality gates, ADR and this evidence report. No new backend service, server upload route, storage, database or universal engine framework was added.

Known risks: large mobile batches can still exceed tab memory; physical iOS/Android devices have not been measured. JPEG is re-encoded and may grow or lose detail. Browser color conversion does not preserve archival ICC/CMYK workflows. Animated images are unsupported. PDF.js preview has a sizable initial download and can fail independently; the verified PDF remains downloadable. Neither processing nor successful local tests authorize merge/release/deployment.
